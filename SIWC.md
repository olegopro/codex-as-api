# Sign in with ChatGPT → public Responses API

Дополнительный **Python-профиль `siwc`** использует официальный OAuth для open-source
клиентов и публичный Responses API с ChatGPT-планом. Сам `codex-as-api` остаётся
сторонним совместимым шлюзом, а не продуктом или одобренным клиентом OpenAI.

Статус ветки: **preview**. Доступность зависит от аккаунта, разрешённых scopes,
политик OpenAI и реально выданного каталога. Публичная API-карточка движка не
доказывает такое же окно или набор инструментов на подписочном маршруте.

## Два явно разделённых профиля

| Профиль | Авторизация | Upstream |
|---|---|---|
| `codex` — по умолчанию | существующий standalone Codex OAuth upstream | ChatGPT Codex backend |
| `siwc` — явно | собственная регистрация и direct ChatGPT-plan grant | `https://api.openai.com/v1` |

Оба профиля используют одну актуальную Python-сборку: переводчик, инструменты,
внешний WebSearch и диагностика общие. Старый пакет 0.9.6 для `codex` не требуется.
Команды `login`, `status` и `preflight` работают с выбранным профилем. Для отдельной
авторизации Legacy до входа задаются:

```sh
export CODEX_AS_API_BACKEND=codex
export CODEX_AS_API_AUTH_PATH="$HOME/.codex-as-api/legacy/auth.json"
.venv/bin/codex-as-api login --open-browser
```

При явно заданном auth-файле native `~/.codex/auth.json` не используется.
У `/health` обоих профилей проверяются `backend`, `upstream_base_url`,
`upstream_transport` и `package_revision` запущенного процесса.
Для Anthropic-запросов Legacy по умолчанию используется полный Responses:
он сохраняет принудительные и параллельные инструменты и параметры изображений.
`thinking.display=omitted` отключает сводку локально; недопустимое upstream
значение `reasoning.summary=none` не отправляется. Зашифрованное рассуждение сохраняется.

Поздние system-сообщения Claude Code в обоих профилях остаются на своём месте
в истории как developer-items. Перенос повторяемых заметок Concise, окружения
и фоновых задач в `instructions` сдвигает историю и теряет её кэш. Проверка только
`cached_tokens > 0` недостаточна: на трёх ходах с инструментами должны сохраняться
начальные instructions и весь прежний input. Это проверяется также с reasoning-items.

Профиль `siwc` **не использует API key или API-кредиты** и не переходит на них
при ошибке. Credentials другого OAuth-клиента не импортируются. TypeScript и Rust
в этой ветке не получают SIWC-поддержку автоматически: адаптация относится к Python.

## Отдельная установка и вход

Для разработки допускается установка ветки; для воспроизводимого запуска
в ссылке зависимости закрепляется проверенный полный commit SHA.

```sh
uv venv .venv
uv pip install --python .venv/bin/python \
  'git+https://github.com/olegopro/codex-as-api.git@siwc-oauth'
```

Профиль и его auth-файл выбираются **до входа**, отдельно от старой установки:

```sh
export CODEX_AS_API_BACKEND=siwc
export CODEX_AS_API_SIWC_AUTH_PATH="$HOME/.codex-as-api/siwc/auth.json"
.venv/bin/codex-as-api login
.venv/bin/codex-as-api status
.venv/bin/codex-as-api preflight
```

Вход требует действия владельца в браузере. Используются PKCE S256, state и nonce;
callback слушает только `127.0.0.1`. Выданный client ID сохраняется вместе с его
регистрацией. Идентификатор хоста создаётся как UUID URN (`urn:uuid:…`), как в
официальном примере; незавершённые регистрации старого формата исправляются при
следующем входе, без изменения уже выданных client ID и токенов.
Не следует копировать client ID из другого приложения или переносить
токены из `~/.codex/auth.json`.

После входа сервер можно проверить на отдельном loopback-порту:

```sh
CODEX_AS_API_HOST=127.0.0.1 CODEX_AS_API_PORT=18081 \
  .venv/bin/codex-as-api
```

`status` — локальное состояние credentials, не проверка отзыва токена и не баланс
подписки. `preflight` проверяет авторизацию и доступность настроенного движка через
GET каталога; при необходимости обновляет grant, но не выполняет генерацию.
Console entrypoint `codex_as_api.cli:main` отключает серверную диагностику до
импорта `server`, когда передана CLI-команда. Поэтому login/status/preflight
не занимают диагностический lock уже работающего шлюза. Запуск сервера без
аргументов сохраняет настроенную диагностику.
Файлы авторизации не должны попадать в git, логи, отчёты или аргументы процесса;
каталог защищается режимом `0700`, файлы — `0600`.

Проверка времени ID token допускает расхождение часов до 30 секунд (`iat`, `nbf`,
`exp`). Подпись, issuer, audience, subject и nonce проверяются по-прежнему;
большее расхождение отклоняется. Без допуска свежий токен на Mini отклонялся
как ещё не выпущенный даже при погрешности 0,3 секунды. Допуск действует при
входе и обновлении credentials; системные часы не меняются.

## Протокол

- Каталог аккаунта: Bearer GET `https://api.openai.com/v1/models`.
- Генерация по умолчанию: `wss://api.openai.com/v1/responses`, событие
  `response.create`, `store:false`, полный `input` на каждом ходу. Сокет сохраняется
  отдельно для аккаунта, сессии (`prompt_cache_key`), модели и ветки разговора.
  Хеш инструкций и начального input до первого user-turn задаёт группу каналов.
  Внутри неё продолжение выбирается по отпечаткам прежнего полного input и ответа:
  одинаковое начало не смешивает разошедшиеся ветки. Точный повтор тоже сохраняет
  тёплый канал; изменённая история получает новый либо холодный канал.
  Хранятся SHA-256, не тексты. Отпечаток ответа учитывает нормализацию Anthropic replay
  (message id/status, JSON аргументов, namespace и группировку text/tools), не меняя
  wire-запрос. История по `previous_response_id` не хранится.
- Прямой контроль 2026-10-31: повтор на том же WebSocket прочитал 1792 из 1926
  токенов; переподключение дало 0 из 1929. HTTP-контроль дал 0. Эти результаты
  относятся к текущему grant и Sol, а не обещают одинаковую экономию каждому плану.
- Один активный запрос на канал. Параллельный запрос получает отдельный канал даже
  при одинаковом начальном промпте; общей очереди родительской сессии нет.
  Разные истории сохраняют собственные тёплые каналы. В подготовленном checkout
  локального потолка по умолчанию нет (`limit=None`); явный числовой limit остаётся
  для ограниченных конфигураций и при насыщении возвращает 429 без очереди.
- Неактивные каналы убираются при следующем обращении после 30 минут простоя;
  LRU-вытеснение по вместимости применяется только при явном числовом limit.
  Канал обновляется при смене токена и перед часовым пределом соединения.
  При вытеснении истёкшие/лишние idle-каналы сразу исключаются из аренды и закрываются
  вне запроса, до восьми одновременно. Короткоживущие workers завершаются после
  опустошения очереди; постоянного уборщика нет. Явный `close()` дожидается очереди
  и workers. Активные каналы idle-очисткой не затрагиваются.
  `/health` сообщает фактический лимит запущенного пула (`upstream_max_connections`)
  и число активных запросов (`upstream_active_requests`).
  `upstream_max_connections=null` означает отсутствие локального потолка.
  Квоты провайдера и ресурсы ОС этим не отменяются; большое число idle-каналов
  увеличивает память и время штатной остановки. Пример 100 каналов/13 волн по 3 с
  относится к ожиданию остановки, а не нового запроса. Локальные регрессии удерживают
  close заблокированным: инициатор и сосед завершаются, затем shutdown ждёт всю очередь.
  Общий AnyIO limiter в unlimited-режиме получает `math.inf` (проверено на 4.15.1),
  включая диагностический HTTP; отдельный limiter отмены на 8 сохранён.
  Явно ограниченный WS-пул получает не меньше `limit + 8` workers.
  Прежняя приёмка 100 каналов/108 workers/429 для 101-го относится к `c1409c0`;
  установленный пакет и рабочие процессы не меняются от этих правок checkout.
- `CODEX_AS_API_SIWC_TRANSPORT=http` — явный диагностический HTTP/SSE; автоматического
  отката на него, legacy или API key нет. Каталог и OAuth остаются HTTP-запросами.
- Явный HTTPS proxy учитывается каталогом и WebSocket. Соединение не перенаправляется
  на ChatGPT `backend-api`; credentials по-прежнему только из SIWC-профиля.
- Инструкции передаются как `instructions`/developer, не system-role input items.
  Только начальные system-сообщения входят в `instructions`. System-сообщения
  внутри истории (окружение, обновления оставшегося бюджета Claude Code) остаются
  на своих местах как developer-items. Перенос меняющегося бюджета в начало
  менял ключ ветки и разрушал тёплый канал на каждом ходу; первая короткая приёмка
  этого не покрыла. Исправление проверено перехватом настоящего клиента на локальных
  заглушках и живым циклом Read → Read → ответ: один канал, 1792/2052 и 1920/2135
  токенов из кэша на продолжениях. Сами инструкции и бюджеты не удаляются.
  Две ветки с поздними system-обновлениями активны одновременно; A прочитала
  1792/2139, B — 1920/2174 на третьем ходе. Второй ход B дал 0 даже на тёплом
  канале: фактическое попадание upstream не гарантируется каждому запросу.
- Function/custom tools приводятся к разрешённому preview формату; namespace содержит
  обязательный непустой `description`. Вызовы и результаты сохраняют имена и call IDs
  на стороне Anthropic-клиента.
- Anthropic input сохраняет порядок чередующихся text/image через `content_parts`;
  assistant text/tool_use/text и reasoning не группируются с потерей позиции.
- Успех требует `response.completed`: EOF, failed/incomplete и потоковая ошибка не
  означают успешного завершения и не завершают недописанный tool-call. Уникальность
  `call_id` проверяется по всем собранным `output_item.done`, даже при пустом
  `completed.output`; ошибочный поздний вызов не выпускает ранние tools клиенту.
- Anthropic SSE отправляет `ping` каждые 10 секунд тишины. Отмена незавершённого
  запроса закрывает его канал, не затрагивая соседние. Закрытие выполняется вне
  event loop с отдельным AnyIO limiter на 8 отмен: занятые приёмниками и каталогом
  общие workers не задерживают отмену. Таймаут SIWC upstream — 600 с.
  Таймер ping не отменяет чтение очереди: кадры данных, ошибки и завершения
  сохраняются даже при совпадении доставки с границей таймера.
  Отмена после `response.completed` не закрывает уже прогретый канал, даже если
  клиент завершил SSE до окончательного закрытия upstream-итератора.
- В журнале — UTC-время, хеши сессии/ветки, request ID, число активных запросов,
  время первого события/дельты и общая длительность. Точные input/cache/output
  приходят в конце; промпты и credentials не пишутся. `/health` сообщает
  `upstream_active_requests` для диагностики, без новых генераций.
  Ревизия `/health` фиксируется при старте процесса: установка нового пакета
  сама по себе не означает, что обслуживающий процесс уже обновлён.
- Общая документация Responses описывает multiplexing через `stream_id`, однако
  текущий SIWC grant 2026-10-31 отклонил его: `Unsupported parameter: stream_id`.
  Поэтому параллельность реализована отдельными сохраняемыми WebSocket. Живая
  проверка двух веток одного движка: обе активны одновременно и обе читают
  1792/1938 токенов повторного входа из кэша. Это не замер списания лимита плана.
- `stop_sequences` Anthropic-фасада обрабатываются локально, включая маркер
  `</block>` внутренних вызовов Claude Code. Клиент получает обрезанный текст,
  `stop_reason: stop_sequence` и сам маркер. Upstream дочитывается до завершения:
  usage учитывает весь фактически созданный вывод, ошибки после маркера не скрываются.
- Запрещённые preview-параметры не отправляются, включая `max_output_tokens`,
  `metadata`, `temperature` и HTTP `previous_response_id`.
- Потолок Anthropic `max_tokens` нельзя объявлять гарантированным upstream cap:
  подписочный preview запрещает `max_output_tokens`.
- Hosted MCP, Responses `tool_search` и другие неподдерживаемые hosted tools не
  появляются от включения этого профиля. Инструменты локального клиента — другой слой.

Набор движков и метаданные окна запрашиваются для текущего аккаунта. Несуществующий
slug не должен молча подменяться другой моделью. Значения default context, maximum
configurable context и effective input budget не взаимозаменяемы.

## Дополнительное ревью 2026-11-01 — подготовлено, не активировано

## Claude Code: updates и диагностика

`thinking.display="updates"` принимается для enabled/adaptive, включая count_tokens.
У Responses нет подтверждённого отдельного канала Anthropic progress notes:
совместимость означает скрытое reasoning (`summary="none"`), а не показ raw/summary
как прогресса. Обычный текст и инструменты сохраняются. Encrypted reasoning
передаётся прежней подписью для replay; старые подписи продолжают читаться.
Неожиданный непустой reasoning в этом режиме — явная протокольная ошибка,
а не скрытая вставка summary в base64-подпись. Семантика summarized/omitted не меняется.

Подробная техническая диагностика включается перед запуском процесса:

```sh
export CODEX_AS_API_DIAGNOSTICS=1
export CODEX_AS_API_DIAGNOSTICS_PATH="$HOME/codex-diagnostics.jsonl"
```

По умолчанию подробный режим выключен. Используется отдельный JSONL-журнал:
сегменты до 5 MiB, цель 7 суток и общий hard cap 256 MiB, права 0600.
При достижении cap раньше недели явно предупреждается о неполном покрытии.
Эксклюзивная `.lock` не допускает двух новых writer на одном пути; старый writer
без блокировки нельзя направлять туда же. После Uvicorn `dictConfig` handler
безопасно открывает поток и блокировку заново; это проверяется detached subprocess.
Тексты запросов/ответов, аргументы инструментов, подписи, заголовки и credentials
не записываются. Дополнительно доступны process/channel IDs, причины affinity,
output-key counters/errors и исходы поиска без query/URL. HTTP correlation ID
связывает валидацию, WS-попытку, кэш, времена и окончание клиентского потока.
`upstream_completed` и HTTP 200 сами по себе не подтверждают успешное окончание
клиентского потока; ошибки/отмены/отключения имеют отдельные исходы.
Причина раннего отказа записывается безопасной категорией и без подробного режима.

Переключение режима — при следующем контролируемом запуске процесса. Установка
пакета не перезапускает шлюз и не меняет уже открытые чаты. Для проверки новой
версии используется отдельное окружение/порт, не обновление файлов живого пакета.

На Pro и Mini отдельные интерактивные чаты выполнили по три хода с Bash:

## Builtin WebSearch Claude Code и возврат после фоновых форков

При явно настроенном `CODEX_AS_API_WEB_SEARCH_COMMAND` (JSON-массив абсолютных argv)
узкий WebSearch-подзапрос Claude Code 2.1.316 обслуживается локальным поисковым процессом.
В stdin передаётся `{query,count}`, ожидается `{results:[{title,url,snippet,date}]}`.
Shell не вызывается; stderr не переносится в публичные ошибки. Поддерживаются hostname
allowed/blocked-фильтры с повторной проверкой выдачи, max_uses, тайм-аут/отмена и предел
ответа 2 MiB. В цепочке claude-api-router используется его `codex-search.py`/`router.search`.
Туда уходит только query, не чат. Это отдельный backend, не hosted-поиск OpenAI/Anthropic.

Клиенту возвращаются обычные результаты со ссылками и `server_tool_use` как факт
реального поиска (для `searchCount`). Зашифрованные ссылки/цитаты Anthropic не выдумываются.
LLM-инференс внутри поиска не выполняется; нулевые token counters и число поисков честны.
Произвольные hosted lifecycle/replay не поддерживаются по-прежнему. Подзапрос распознаётся
не по одному похожему user-тексту, а по инструменту, system-маркеру и точной форме истории.

На канале сохраняются до 16 завершённых fingerprint/output-key якорей. После фонового
форка main может продолжиться по прежнему якорю, без выключения сводок/подсказок.
Активные каналы остаются эксклюзивными; закрытие очищает якоря, полный input не меняется.
Непотоковый Messages после чтения тела отслеживает client disconnect и использует
отдельный limiter отмены. Открытый сокет не считается отменой; поздняя отмена после
completed не закрывает тёплый WS. Закрытие сокета не доказывает остановку upstream-расхода.

## Безопасная миграция

Старую установку и её credentials следует сохранить. Новый профиль проверяется
на отдельном порту; действующий сервер не заменяется просто ради установки пакета.
Перед продолжением старого чата отдельно проверяется перенос encrypted reasoning:
совпадение имени движка само по себе не доказывает переносимость opaque items.

Минимальная проверка — короткий синтетический tool-roundtrip и продолжение в обе
стороны. Для определения окна не требуются промпты на сотни тысяч токенов. Если
каталог не сообщает достоверный предел, большой лимит не следует выдумывать.
